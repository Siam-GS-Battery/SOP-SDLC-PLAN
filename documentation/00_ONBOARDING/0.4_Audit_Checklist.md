## 1. Sprint Planning & Task Assignment

> **ผู้รับผิดชอบ:** Sr. Engineer + PM  
> **ตรวจเมื่อ:** ต้น Sprint (Sprint Planning Meeting)

| # | รายการตรวจสอบ | ✅ | หมายเหตุ |
|:-:|:---|:-:|:---|
| 1.1 | Sprint Planning จัดทุกวันจันทร์ (30 นาที) | ☐ | |
| 1.2 | Sr. แตก task ใหญ่ให้ Jr. ทำจบได้ใน 1-3 วัน | ☐ | |
| 1.3 | ทุก task มี Acceptance Criteria ชัดเจน | ☐ | |
| 1.4 | ทุก task เชื่อมกับ User Story ใน Asana | ☐ | |
| 1.5 | Sr. กำหนด Architecture / Design Pattern ก่อนเริ่มงาน | ☐ | |
| 1.6 | Task มี Priority (MoSCoW) กำกับ | ☐ | |

## 2. Definition of Ready (DoR) Compliance

> **ผู้รับผิดชอบ:** Sr. Engineer ตรวจก่อน Jr. เริ่ม code  
> **ตรวจเมื่อ:** ก่อนเริ่มพัฒนาทุก task  
> **อ้างอิง:** [1.5 Definition of Ready & Done](../01_REQUIREMENTS/1.5_Definition_of_Ready_Done.md)

| # | รายการตรวจสอบ | ✅ | หมายเหตุ |
|:-:|:---|:-:|:---|
| 2.1 | Requirement ชัดเจน ไม่ต้องเดา | ☐ | |
| 2.2 | Acceptance Criteria ระบุไว้ครบ | ☐ | |
| 2.3 | Figma / Wireframe พร้อม (ถ้าเป็นงาน UI) | ☐ | |
| 2.4 | API Spec / ERD พร้อม (ถ้าเป็นงาน Backend) | ☐ | |
| 2.5 | ไม่มี dependency ที่ยัง block อยู่ | ☐ | |
| 2.6 | Task estimate สมเหตุสมผล (1-3 วัน) | ☐ | |

## 3. Development Flow

> **ผู้รับผิดชอบ:** Jr. Engineer (Sr. คอย monitor)  
> **ตรวจเมื่อ:** ระหว่าง Sprint

| # | รายการตรวจสอบ | ✅ | หมายเหตุ |
|:-:|:---|:-:|:---|
| 3.1 | Jr. สร้าง branch ตาม naming convention (`feature/`, `bugfix/`, `hotfix/`) | ☐ | |
| 3.2 | Commit message ตาม convention (type: description) | ☐ | |
| 3.3 | Commit บ่อยทุก 1-2 ชั่วโมง | ☐ | |
| 3.4 | Jr. pull latest จาก staging ทุกเช้า | ☐ | |
| 3.5 | Jr. เขียน Unit Test สำหรับ code ตัวเอง | ☐ | |
| 3.6 | ไม่มี hardcode ค่า — ใช้ env variables | ☐ | |
| 3.7 | ไม่มี debug code / console.log หลุดไป | ☐ | |
| 3.8 | PR เปิดเป็น Draft ถ้ายังไม่เสร็จ | ☐ | |

## 4. Code Review (Sr. Responsibility)

> **ผู้รับผิดชอบ:** Sr. Engineer  
> **ตรวจเมื่อ:** ทุก PR ก่อน merge  
> **อ้างอิง:** [7.4 Code Review Guidelines](../07_GIT_WORKFLOW/7.4_Code_Review_Guidelines.md)

| # | รายการตรวจสอบ | ✅ | หมายเหตุ |
|:-:|:---|:-:|:---|
| 4.1 | Sr. review PR ภายใน 24 ชั่วโมง (Hotfix < 2 ชม., Urgent < 4 ชม.) | ☐ | |
| 4.2 | ตรวจ Logic ถูกต้อง — ไม่มี edge case ตกหล่น | ☐ | |
| 4.3 | ตรวจ Security — ไม่มี SQL Injection, XSS, secrets ใน code | ☐ | |
| 4.4 | ตรวจ Readability — ชื่อตัวแปร/ฟังก์ชันสื่อความหมาย | ☐ | |
| 4.5 | ตรวจ Test Coverage — มี unit test ครอบคลุม | ☐ | |
| 4.6 | ตรวจ Code Standard — ตาม coding convention ของทีม | ☐ | |
| 4.7 | ใช้ Comment Level ถูกต้อง (MUST / SHOULD / NIT / LEARN) | ☐ | |
| 4.8 | ให้ feedback เชิงสร้างสรรค์ — บอก "ทำไม" ไม่ใช่แค่ "ผิด" | ☐ | |
| 4.9 | ไม่มี Jr. merge PR เอง (Sr. ต้องเป็นคน approve + merge) | ☐ | |

## 5. Definition of Done (DoD) Compliance

> **ผู้รับผิดชอบ:** Sr. Engineer ตรวจก่อน merge  
> **ตรวจเมื่อ:** ก่อน merge ทุก PR  
> **อ้างอิง:** [1.5 Definition of Ready & Done](../01_REQUIREMENTS/1.5_Definition_of_Ready_Done.md)

| # | รายการตรวจสอบ | ✅ | หมายเหตุ |
|:-:|:---|:-:|:---|
| 5.1 | Code ทำงานได้ตาม Acceptance Criteria ทุกข้อ | ☐ | |
| 5.2 | Unit Test ผ่านครบ | ☐ | |
| 5.3 | CI Pipeline (Tests + Lint) ผ่าน | ☐ | |
| 5.4 | ไม่มี debug code / console.log / TODO หลุด | ☐ | |
| 5.5 | Sr. review และ approve แล้ว | ☐ | |
| 5.6 | Asana ticket linked กับ PR | ☐ | |
| 5.7 | Documentation อัปเดตแล้ว (ถ้ามี) | ☐ | |
| 5.8 | **UI:** Responsive + ตรง Figma | ☐ | ถ้าเป็นงาน UI |
| 5.9 | **API:** Response format ถูกต้อง + Error handling ครบ | ☐ | ถ้าเป็นงาน API |
| 5.10 | **Bug Fix:** ไม่มี regression + มี test case กัน | ☐ | ถ้าเป็น bug fix |

> **ผู้รับผิดชอบ:** Sr. Engineer + DevOps  
> **ตรวจเมื่อ:** ก่อนและหลัง deploy  
> **อ้างอิง:** [5.2 Pre-Deploy Checklist](../05_DEPLOY/5.2_Pre_Deploy_Checklist.md)

| # | รายการตรวจสอบ | ✅ | หมายเหตุ |
|:-:|:---|:-:|:---|
| 6.1 | Build ผ่านบน local ก่อน deploy | ☐ | |
| 6.2 | TypeScript check ไม่มี error | ☐ | |
| 6.3 | Environment variables ครบถ้วนและถูกต้อง | ☐ | |
| 6.4 | Database migration รันเรียบร้อย (ถ้ามี) | ☐ | |
| 6.5 | Health check endpoint ตอบ OK หลัง deploy | ☐ | |
| 6.6 | ไม่ push ตรงไป main/staging — ต้องผ่าน PR เท่านั้น | ☐ | |
| 6.7 | Rollback plan เตรียมไว้แล้ว | ☐ | |

## 9. Security & Access Control

> **ผู้รับผิดชอบ:** Sr. Engineer  
> **ตรวจเมื่อ:** รายเดือน หรือเมื่อมี release ใหญ่

| # | รายการตรวจสอบ | ✅ | หมายเหตุ |
|:-:|:---|:-:|:---|
| 9.1 | ไม่มี credentials / API keys / passwords ใน codebase | ☐ | |
| 9.2 | ทุกคนเปิด 2FA ใน GitHub / ระบบสำคัญ | ☐ | |
| 9.3 | Access rights เหมาะสมตาม role (least privilege) | ☐ | |
| 9.4 | Dependencies ไม่มี known vulnerability (npm audit / dependabot) | ☐ | |
| 9.5 | .env ไม่ถูก commit เข้า Git (.gitignore ครอบคลุม) | ☐ | |

## 10. วิธีใช้ Checklist นี้

### ใช้ตรวจเมื่อไหร่?

| ความถี่ | Section ที่ต้องตรวจ | ผู้ตรวจ |
|:--------|:-------------------|:--------|
| **ทุก PR** | 4, 5 | Sr. Engineer |
| **ทุก Sprint** | 1, 2, 3, 7 | Sr. Engineer + PM |
| **ก่อน Deploy** | 6 | Sr. Engineer + DevOps |
| **รายเดือน** | 8, 9 | Team Lead |

### Flow การ Audit

```
1. คัดลอก checklist ของ section ที่ต้องตรวจ
2. ตรวจทีละข้อ — ติ๊ก ✅ ถ้าผ่าน
3. ถ้าไม่ผ่าน → เขียนหมายเหตุว่าติดตรงไหน
4. สรุปผลส่ง Team Lead / PM
5. สร้าง action item ใน Asana สำหรับข้อที่ไม่ผ่าน
6. ติดตามใน Sprint ถัดไป
```

### ตัวอย่างสถานะ

| สัญลักษณ์ | ความหมาย |
|:---------:|:---------|
| ✅ | ผ่าน — ปฏิบัติตาม SOP |
| ❌ | ไม่ผ่าน — ต้องแก้ไข |
| ⚠️ | ผ่านบางส่วน — ต้องปรับปรุง |
| N/A | ไม่เกี่ยวข้องกับ task นี้ |

## Quick Reference — Sr. Engineer ต้องตรวจอะไรบ้าง?

> สรุปสั้นๆ สำหรับ Sr. ใช้ตรวจตัวเองทุกวัน

- [ ] Task แตกให้ Jr. เหมาะสม (1-3 วัน)?
- [ ] DoR ครบก่อนให้ Jr. เริ่มงาน?
- [ ] Review PR ภายใน 24 ชม.?
- [ ] ตรวจ Logic + Security + Test + Standards?
- [ ] ให้ feedback สร้างสรรค์?
- [ ] DoD ครบก่อน merge?
- [ ] Unblock Jr. ภายใน 30 นาที?
- [ ] Documentation อัปเดต?
