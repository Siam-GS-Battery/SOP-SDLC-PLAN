### วิธีมอบหมายงาน (Task Assignment Protocol)

#### Output ที่ชัดเจน

| | ตัวอย่าง |
|---|----------|
| **Don't** ❌ | "ทำ login feature" |
| **Do** ✅ | "ทำ login feature" พร้อมระบุ Acceptance Criteria ชัดเจน เช่น login สำเร็จ → คืน 200 + JWT token, password ผิด → คืน 401 + error message |

#### Time Estimate

- ประเมินเวลาร่วมกัน ไม่ใช่ Senior กำหนดฝ่ายเดียว
- ถ้าน้องรู้สึกว่านานกว่า → คุยและปรับด้วยกัน

#### กฎเพิ่มเติม

- Junior ไม่ควรมี In Progress เกิน **2 ticket** พร้อมกัน
- Task ที่ใหญ่กว่า **3 วัน** → Senior ต้อง break down ก่อนเสมอ


### กฎ 30 นาที (Golden Rule)

> **ถ้าติดปัญหาเกิน 30 นาที ต้องแจ้ง Senior ทันที**
> นี่ไม่ใช่ความล้มเหลว หรือการรบกวน — แต่นี่คือสิ่งที่ถูกต้องและคาดหวังให้ทำ

#### วิธีขอความช่วยเหลือที่ถูกต้อง

| | ตัวอย่าง |
|---|----------|
| **ไม่ควรทำ** ❌ | "พี่ครับ ทำไม่ได้ครับ" (กว้างเกินไป Senior ต้องไล่ถามใหม่หมด) |
| **ควรทำ** ✅ | "พี่ครับ ผมพยายามทำ **[X]** ติดตรงที่ **[Y]** เพราะ error: **[Z]** ผมลองแก้ด้วยวิธี **[A]** และ **[B]** แล้ว แต่ยังไม่ได้ผล พี่พอมีแนวทางแนะนำไหมครับ?" |

### Team Rules — ข้อตกลงสำคัญของทีม

#### DO — สิ่งที่ต้องทำเสมอ

- ทุก code ต้องผ่าน **PR ก่อน merge** ไม่มีข้อยกเว้น
- ทุก PR ต้องผ่าน **CI (Test & Lint)** ก่อน request review
- Commit บ่อยๆ **ทุก 1–2 ชม.** อย่ารอเสร็จทั้งหมด
- ติดปัญหาเกิน **30 นาที** ต้องแจ้ง Senior ทันที
- ดึง code ล่าสุดจาก **staging** ทุกเช้าก่อนเริ่มงาน

#### DON'T — สิ่งที่ห้ามเด็ดขาด

- ห้าม push ตรง **main หรือ staging** โดยไม่ผ่าน PR
- ห้าม **merge PR ตัวเอง** แม้จะเร่งด่วนแค่ไหน
- ห้าม commit **secret, API key, password** ลง git
- ห้าม **ช่อน blocker** ไว้คนเดียวเกิน 30 นาที
- ห้าม **hardcode value** ที่ควรเป็น environment variable
- ห้ามเปิด PR ที่ยังไม่เสร็จโดยไม่ mark เป็น **Draft**
