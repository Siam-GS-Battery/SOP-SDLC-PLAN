# 1.3 Acceptance Criteria

## วิธีการเขียน
Acceptance Criteria (AC) คือเงื่อนไขที่ต้องผ่านเพื่อถือว่า User Story เสร็จสมบูรณ์ ("Definition of Done")

**มาตรฐานอ้างอิง:**
- **Behavior-Driven Development (BDD)**: Dan North (2003) - Origin of Given-When-Then
- **Gherkin Syntax**: Cucumber framework - Dan North & Aslak Hellesøy (2008)
- **INVEST Criteria - "T" (Testable)**: Bill Wake (2003) - AC ทำให้ story ทดสอบได้
- **Definition of Done**: Scrum Guide (Scrum.org) - Clear completion criteria
- **ATDD (Acceptance Test-Driven Development)**: Kent Beck - Specification by Example

### รูปแบบการเขียน:

#### 1. **Given-When-Then Format** (Gherkin Syntax - BDD Standard):
- **Given**: สถานการณ์เริ่มต้น (Precondition/Context)
- **When**: เหตุการณ์/การกระทำ (Action/Event)
- **Then**: ผลลัพธ์ที่คาดหวัง (Expected Outcome)

**ที่มา**: Dan North (2003) - Behavior-Driven Development

#### 2. **Checklist Format**:
- รายการเช็คลิสต์ที่ต้องผ่านทั้งหมด
- แยกเป็น Functional และ Non-Functional Requirements
- ใช้ `[ ]` สำหรับยังไม่เสร็จ, `[x]` สำหรับเสร็จแล้ว

## ตัวอย่างเอกสาร

### US-001: User Login with Email and Password

**Story**: As a user, I want to login with email and password, so that I can securely access my account

#### Acceptance Criteria:

| AC ID | Scenario | Given | When | Then | Status |
|---|---|---|---|---|---|
| AC-001-01 | Successful login with valid credentials | User is on the login page | User enters valid email and password and clicks "Login" | System authenticates user and redirects to dashboard | ✓ Pass |
| AC-001-02 | Failed login with invalid email | User is on the login page | User enters invalid email format | System displays error message "Invalid email format" | ✓ Pass |
| AC-001-03 | Failed login with wrong password | User is on the login page | User enters correct email but wrong password | System displays error message "Incorrect email or password" | ✓ Pass |
| AC-001-04 | Failed login with empty fields | User is on the login page | User clicks "Login" without entering credentials | System displays error message "Email and password are required" | ✓ Pass |
| AC-001-05 | Password visibility toggle | User is on the login page | User clicks the eye icon in password field | Password text toggles between visible and hidden | ✓ Pass |
| AC-001-06 | Account lockout after failed attempts | User has failed login 5 times | User attempts to login again | System displays "Account locked. Please try again in 15 minutes" | ✓ Pass |

#### Additional Acceptance Criteria (Checklist):
- [ ] Login form includes email and password fields
- [x] Password field is masked by default
- [x] "Remember me" checkbox is functional
- [x] "Forgot password" link is visible and clickable
- [x] Form validates email format (RFC 5322 standard)
- [x] Session expires after 30 minutes of inactivity
- [x] System logs all login attempts (successful and failed)
- [ ] Login works on mobile devices (responsive)
- [x] Loading indicator shows during authentication
- [x] Error messages are clear and user-friendly

### US-002: Password Reset via Email

**Story**: As a user, I want to reset my password via email, so that I can recover my account if I forget my password

#### Acceptance Criteria:

| AC ID | Scenario | Given | When | Then | Status |
|---|---|---|---|---|---|
| AC-002-01 | Successful password reset request | User is on "Forgot Password" page | User enters registered email and clicks "Send Reset Link" | System sends reset email and shows confirmation message | ✓ Pass |
| AC-002-02 | Invalid email address | User is on "Forgot Password" page | User enters unregistered email | System shows "If email exists, reset link has been sent" (security) | ✓ Pass |
| AC-002-03 | Reset link expiration | User received reset email 25 hours ago | User clicks on reset link | System shows "Reset link has expired. Please request a new one" | ✓ Pass |
| AC-002-04 | Successful password change | User clicks valid reset link | User enters new password (meets requirements) and confirms | System updates password and shows success message | ✓ Pass |
| AC-002-05 | Password complexity validation | User is on reset password page | User enters weak password (e.g., "123456") | System shows "Password must be at least 8 characters with uppercase, lowercase, and number" | ✓ Pass |
| AC-002-06 | Password confirmation mismatch | User is on reset password page | User enters different passwords in "password" and "confirm" fields | System shows "Passwords do not match" | ✓ Pass |

#### Additional Acceptance Criteria (Checklist):
- [x] Reset link expires after 24 hours
- [x] Reset link can only be used once
- [x] Email contains clear instructions
- [x] Email is sent within 5 minutes
- [x] Password requirements are displayed on the form
- [x] Old password cannot be reused immediately
- [x] System invalidates all existing sessions after reset
- [ ] Email includes sender information
- [x] Link redirects to HTTPS page

### US-003: Admin Dashboard with Key Metrics

**Story**: As an admin, I want to see a dashboard with key metrics, so that I can monitor system performance at a glance

#### Acceptance Criteria:

| AC ID | Scenario | Given | When | Then | Status |
|---|---|---|---|---|---|
| AC-003-01 | Dashboard loads with metrics | Admin is logged in | Admin navigates to dashboard | System displays all key metrics (users, revenue, active sessions, errors) | ⏳ In Progress |
| AC-003-02 | Real-time data updates | Admin is viewing dashboard | System data changes (e.g., new user registers) | Dashboard updates automatically within 5 seconds | ⏳ In Progress |
| AC-003-03 | Date range filter | Admin is on dashboard | Admin selects custom date range (e.g., Last 7 days) | Metrics update to show data for selected period | ⏳ In Progress |
| AC-003-04 | Export dashboard data | Admin is viewing dashboard | Admin clicks "Export" button | System downloads CSV file with current metrics | 📋 To Do |
| AC-003-05 | Chart interaction | Admin is viewing dashboard | Admin hovers over chart data points | System shows tooltip with detailed information | 📋 To Do |
| AC-003-06 | Empty state handling | Admin views dashboard with no data | No data available for selected period | System displays "No data available for this period" message | 📋 To Do |

#### Additional Acceptance Criteria (Checklist):
- [x] Dashboard loads within 3 seconds
- [ ] Metrics include: Total Users, Active Sessions, Revenue (MTD), Error Rate
- [x] Charts are responsive and mobile-friendly
- [ ] Color scheme follows brand guidelines
- [ ] Metrics are accurate (verified against database)
- [ ] Loading skeleton appears while data is loading
- [ ] Error messages display if API fails
- [ ] Refresh button available to manually update data

**Status Legend:**
- ✓ Pass: ผ่านการทดสอบแล้ว
- ⏳ In Progress: กำลังพัฒนา/ทดสอบ
- 📋 To Do: ยังไม่ได้เริ่มทำ
- ✗ Fail: ไม่ผ่านการทดสอบ

## วิธีการเขียน Acceptance Criteria

### โครงสร้างตาราง (Given-When-Then Format):
1. **AC ID**: รหัสอ้างอิง (AC-XXX-01, AC-XXX-02...)
2. **Scenario**: ชื่อสถานการณ์ที่ทดสอบ
3. **Given**: สถานการณ์เริ่มต้น/เงื่อนไขก่อนทำ
4. **When**: การกระทำ/เหตุการณ์ที่เกิดขึ้น
5. **Then**: ผลลัพธ์ที่คาดหวัง
6. **Status**: สถานะการทดสอบ (Pass/In Progress/To Do/Fail)

### โครงสร้าง Checklist:
- ใช้สำหรับ Functional และ Non-Functional Requirements
- แยกเป็นหมวดหมู่ชัดเจน
- ใช้ `[ ]` สำหรับยังไม่เสร็จ และ `[x]` สำหรับเสร็จแล้ว

## AC Writing Best Practices

### INVEST "T" - Testable (Bill Wake, 2003)
Acceptance Criteria ต้องทำให้ User Story **ทดสอบได้** (Testable) - หัวใจของ INVEST

### ✓ DO (Best Practices):
- **เขียนให้ชัดเจนและทดสอบได้** - สามารถเขียน Test Case หรือ Automated Test ได้ทันที
- **ครอบคลุมทุก Scenario** - รวม:
  - **Happy Path**: กรณีปกติที่ผู้ใช้ทำถูกต้อง
  - **Error Cases**: กรณีที่ผู้ใช้ทำผิดพลาด
  - **Edge Cases**: กรณีขอบเขต (เช่น ค่าสูงสุด/ต่ำสุด, empty, null)
- **ใช้ภาษาที่เข้าใจง่าย** - ทุกคนในทีมเข้าใจเหมือนกัน (Business + Dev + QA)
- **ระบุค่าเฉพาะเจาะจง (Quantifiable)** - เช่น:
  - ✓ "loads within 3 seconds"
  - ✗ "loads quickly"
- **แยก AC เป็นข้อๆ** - อย่ารวมหลายเงื่อนไขในข้อเดียว (Single Responsibility)
- **ใช้ Given-When-Then** - ตาม Gherkin Syntax เพื่อความชัดเจน
- **เขียนก่อนพัฒนา** - AC เป็นส่วนหนึ่งของ Story ไม่ใช่เขียนหลังเสร็จ

### ✗ DON'T (Common Mistakes):
- **เขียนคลุมเครือ** - "ระบบทำงานได้ดี" ← ไม่ชัดเจน, วัดผลไม่ได้
- **ข้ามส่วนสำคัญ** - ลืมทดสอบ Error Handling, Validation, Security
- **เขียนเป็นภาษาเทคนิคมากเกินไป** - AC ควรเข้าใจได้แม้ไม่ใช่นักพัฒนา
- **ไม่ระบุเกณฑ์วัด** - ต้องรู้ว่า "ผ่าน" หรือ "ไม่ผ่าน" ยังไง (Binary: Yes/No)
- **รวมหลายเงื่อนไขในข้อเดียว** - ทำให้ทดสอบยาก
- **เขียน AC เป็น Solution** - AC บอก "อะไร" (What) ไม่ใช่ "อย่างไร" (How)

## Template สำหรับเขียน AC ใหม่

### Format 1: Given-When-Then (Table Format)

```markdown
| AC ID | Scenario | Given | When | Then | Status |
|-------|----------|-------|------|------|--------|
| AC-XXX-01 | [ชื่อ scenario] | [สถานะเริ่มต้น/Context] | [การกระทำ/Event] | [ผลลัพธ์ที่คาดหวัง/Outcome] | [Pass/Fail/To Do] |
```

### Format 2: Checklist Format

```markdown
#### Functional Requirements:
- [ ] ข้อกำหนดหน้าที่การทำงานที่ 1
- [ ] ข้อกำหนดหน้าที่การทำงานที่ 2

#### Non-Functional Requirements:
- [ ] Performance: [เช่น Response time < 2s]
- [ ] Security: [เช่น Data encrypted at rest]
- [ ] Usability: [เช่น Accessible to screen readers]
- [ ] Scalability: [เช่น Handle 1000 concurrent users]
```

### Format 3: Gherkin Syntax (BDD Format)

**Standard Cucumber/BDD Format:**

```gherkin
Scenario: [Scenario Name - ชื่อสถานการณ์]
  Given [precondition - เงื่อนไขเริ่มต้น]
  When [action - การกระทำ]
  Then [expected result - ผลลัพธ์ที่คาดหวัง]
  And [additional result - ผลลัพธ์เพิ่มเติม]
  But [exception - ข้อยกเว้น]
```

**Example:**
```gherkin
Scenario: Successful login with valid credentials
  Given user is on the login page
  And user has a valid account
  When user enters correct email "test@example.com"
  And user enters correct password "Pass123!"
  And user clicks "Login" button
  Then system authenticates the user
  And user is redirected to dashboard
  And session is created with 30-minute expiry
```

## ตัวอย่าง AC ที่ดี vs ไม่ดี

### ✓ GOOD EXAMPLE (Specific & Testable):

```gherkin
Scenario: Password must meet complexity requirements
  Given user is on password reset page
  When user enters password "abc123"
  Then system displays error "Password must be at least 8 characters with uppercase, lowercase, and number"
  And submit button is disabled
```

**ทำไมดี:**
- ✓ Specific: ระบุค่าชัดเจน (8 characters, uppercase, lowercase, number)
- ✓ Testable: ทดสอบได้ทันทีด้วย test case
- ✓ Clear outcome: รู้ว่าต้อง show error message + disable button

---

### ✗ BAD EXAMPLE (Vague & Not Testable):

```markdown
- Password should be secure
```

**ทำไมไม่ดี:**
- ✗ Vague: "secure" คืออะไร? ยาวแค่ไหน? มีอักขระพิเศษหรือไม่?
- ✗ Not Testable: ไม่รู้ว่าจะทดสอบยังไง
- ✗ No clear outcome: ไม่รู้ว่าผ่านหรือไม่ผ่าน

**✓ แก้ไข:**
```gherkin
Scenario: Password complexity validation
  Given user is creating a new password
  When user enters password
  Then password must be at least 8 characters long
  And contain at least one uppercase letter (A-Z)
  And contain at least one lowercase letter (a-z)
  And contain at least one number (0-9)
  And optionally contain special characters (!@#$%^&*)
```

## มาตรฐานและแนวทางที่ใช้อ้างอิง

### Behavior-Driven Development (BDD):
- **Dan North** (2003): Introduced BDD and Given-When-Then format
- **Cucumber Framework**: Gherkin syntax standard (Dan North & Aslak Hellesøy, 2008)
- **SpecFlow**: BDD framework for .NET
- **Behat**: BDD framework for PHP

### Acceptance Testing Standards:
- **ATDD (Acceptance Test-Driven Development)**: Kent Beck - Test-first approach
- **Specification by Example**: Gojko Adzic (2011) - Collaborative specification
- **TDD (Test-Driven Development)**: Kent Beck (1999) - Write tests before code

### Quality Attributes:
- **ISO/IEC 25010**: Software Quality Model (Functional & Non-Functional requirements)
- **INVEST "T" (Testable)**: Bill Wake (2003) - User stories must be testable
- **Definition of Done**: Scrum Guide - Clear completion criteria

### Testing Frameworks:
- **Cucumber**: BDD testing framework (Ruby, Java, JavaScript)
- **Playwright/Cypress**: E2E testing frameworks (can use Gherkin syntax)
- **JUnit/TestNG**: Unit testing with BDD support
- **RSpec**: BDD testing framework for Ruby

### Industry Best Practices:
- **3 Amigos Meeting**: Product Owner + Developer + Tester collaborate on AC
- **Shift-Left Testing**: Write AC early in the development cycle
- **Living Documentation**: AC becomes automated tests and documentation
