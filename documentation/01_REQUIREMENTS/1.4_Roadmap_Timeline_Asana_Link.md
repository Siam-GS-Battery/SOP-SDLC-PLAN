## วิธีสร้าง Project Roadmap

### ขั้นตอนที่ 1: แบ่งโปรเจกต์ตาม SDLC Phase

ทำงานตามลำดับ SDLC Phase ของทีม ซึ่งตรงกับโครงสร้างเอกสาร SOP:

```mermaid
flowchart LR
    A["Phase 1\nRequirements"] --> B["Phase 2\nDesign"]
    B --> C["Phase 3\nDatabase"]
    C --> D["Phase 4\nDevelopment"]
    D --> E["Phase 5\nDeploy"]
    E --> F["Phase 6\nTesting"]
```

| SDLC Phase | เอกสาร SOP | กิจกรรมหลัก | ใครทำ | Duration แนะนำ |
|:-----------|:-----------|:-----------|:------|:---------------|
| **Phase 1 — Requirements** | [Ch.1](../01_REQUIREMENTS/INDEX.md) | เก็บ Requirement, เขียน User Story, กำหนด AC, สร้าง DoR/DoD | PM + Senior | 1–2 สัปดาห์ |
| **Phase 2 — Design** | [Ch.2](../02_DESIGN/INDEX.md) | สร้าง Wireframe + UI Design ด้วย Figma Make | Senior + PM | 1–2 สัปดาห์ |
| **Phase 3 — Database** | [Ch.3](../03_DATABASE/INDEX.md) | ออกแบบ ERD, Schema, Migration | Senior | 1 สัปดาห์ |
| **Phase 4 — Development** | [Ch.4](../04_DEVELOPMENT/INDEX.md) | พัฒนา Frontend, Backend, API, Integration | Junior + Senior | 4–8 สัปดาห์ |
| **Phase 5 — Deploy** | [Ch.5](../05_DEPLOY/INDEX.md) | Deploy to Staging → Production, Smoke Test | Senior | 1 สัปดาห์ |
| **Phase 6 — Testing** | [Ch.6](../06_TESTING/INDEX.md) | Unit Test, Integration Test, UAT | Junior + PM | 1–2 สัปดาห์ |

> **หมายเหตุ:** Phase 4 (Development) กับ Phase 6 (Testing) ทำคู่กันได้ — Junior เขียน test ควบคู่กับ code ไม่ต้องรอ Phase 6 ถึงค่อยเริ่ม test
>
> [Ch.7 Git Workflow](../07_GIT_WORKFLOW/INDEX.md) ใช้ตลอดทุก Phase ตั้งแต่ Phase 4 เป็นต้นไป

### ขั้นตอนที่ 2: กำหนด Milestone แต่ละ Phase

Milestone คือจุดสำคัญที่ต้อง "เสร็จ" ก่อนไปต่อ:

**ตัวอย่าง Kaizen Web Application:**

| Milestone | เงื่อนไขผ่าน | Phase |
|:----------|:-----------|:------|
| Requirements Sign-off | PM + Stakeholder อนุมัติ User Stories + AC + DoR/DoD | Phase 1 |
| Design Approved | ทีม review Wireframe/UI จาก Figma Make ผ่าน | Phase 2 |
| Database Ready | ERD + Schema + Migration เสร็จ ทีม review ผ่าน | Phase 3 |
| Frontend Demo Ready | หน้าเว็บทำงานได้ด้วย mock data | Phase 4 |
| API Ready | CRUD endpoints ทำงานได้จริง + มี test | Phase 4 |
| Full-stack Integration | Frontend เชื่อมกับ API สำเร็จ | Phase 4 |
| Testing Passed | ผ่าน Quality Gates (CI + Senior Review) | Phase 6 |
| UAT Sign-off | Stakeholder ทดสอบแล้วอนุมัติ | Phase 6 |
| Production Launch | Deploy to Production สำเร็จ + Smoke Test ผ่าน | Phase 5 |

## การตั้ง Asana สำหรับโปรเจกต์

### Board Structure

สร้าง Asana Project 1 ตัวต่อ 1 โปรเจกต์:

```
📋 Kaizen Web Application (Project)
├── Sections (แบ่งตาม SDLC Phase)
│   ├── Phase 1 - Requirements
│   ├── Phase 2 - Design
│   ├── Phase 3 - Database
│   ├── Phase 4 - Development
│   ├── Phase 5 - Deploy
│   └── Phase 6 - Testing
│
├── Views
│   ├── Board View    → ดูสถานะ (To Do / In Progress / Done)
│   ├── Timeline View → ดู Gantt Chart
│   └── List View     → ดูรายการทั้งหมด
│
└── Custom Fields
    ├── Phase          → Phase 1-5
    ├── Priority       → High / Medium / Low
    ├── Sprint         → Sprint 1, 2, 3...
    └── Story Points   → 1, 2, 3, 5, 8, 13
```

### Sprint Board View

นอกจากแบ่งตาม Phase ใช้ **Board View** สำหรับ Sprint ปัจจุบัน:

| Column | ความหมาย |
|:-------|:---------|
| **Backlog** | งานที่ยังไม่ได้จัดเข้า Sprint |
| **To Do** | งานของ Sprint นี้ ยังไม่เริ่ม |
| **In Progress** | กำลังทำอยู่ |
| **In Review** | เปิด PR แล้ว รอ Senior Review |
| **Done** | Merge แล้ว เสร็จสมบูรณ์ |

## วิธีใช้ Asana ในแต่ละจังหวะ

### Sprint Planning (ทุกวันจันทร์เช้า)

1. ดู **Timeline View** — Phase นี้ต้องทำ milestone ไหน
2. ดึง Task จาก **Backlog** — เลือก task ที่ตอบโจทย์ milestone
3. ย้ายเข้า **To Do** — กำหนด Sprint tag
4. **Assign + Estimate** — กำหนดคนรับผิดชอบ + ประเมินเวลาร่วมกัน

### Daily Flow

```
ทุกเช้า: ดึง code ล่าสุดจาก staging
→ เปิด Asana ดู task ของตัวเอง
→ ย้าย task เป็น "In Progress"
→ สร้าง branch ตาม Asana Task ID
→ ทำงาน + commit ทุก 1-2 ชม.
→ เสร็จ → เปิด PR ลิงก์ Asana Task
→ ย้าย task เป็น "In Review"
```

### Sprint Review (ทุก 2 สัปดาห์)

1. **Demo** สิ่งที่ทำเสร็จใน Sprint
2. **เทียบกับ Milestone** — ใกล้ถึง milestone ไหนแล้ว
3. **ปรับแผน** — ถ้า milestone เลื่อนให้ปรับ priority ใน Sprint ถัดไป

## Naming Convention ใน Asana

### Task Title

```
[Type] ชื่อ task สั้นกระชับ
```

**ตัวอย่าง:**
- `[Feature] สร้างหน้า Login`
- `[Feature] CRUD API สำหรับ Users`
- `[Bug] แก้ปัญหา null response ใน payment API`
- `[Chore] ตั้งค่า CI pipeline`
- `[Docs] เขียน API Documentation`

### Task Description Template

```markdown
## สิ่งที่ต้องทำ
- รายละเอียดงาน

## Acceptance Criteria
- [ ] เงื่อนไขที่ต้องผ่าน

## Reference
- Figma: [ลิงก์ ถ้ามี]
- API Spec: [ลิงก์ ถ้ามี]
```

> ดูรายละเอียดเรื่อง DoR ของ Task ที่ [1.5 Definition of Ready & Done](1.5_Definition_of_Ready_Done.md)

## การติดตามความคืบหน้า

### Weekly Check (ทุกวันศุกร์)

| สิ่งที่ดู | ดูที่ไหน |
|:---------|:---------|
| Task ที่ค้าง In Progress นานเกินไป | Asana Board View |
| PR ที่รอ review เกิน 24 ชม. | GitHub Pull Requests |
| Milestone ถัดไปคืบหน้าแค่ไหน | Asana Timeline View |

### Milestone Review (เมื่อถึง Milestone)

1. ตรวจสอบว่าผ่านเงื่อนไข Milestone หรือไม่
2. ถ้าผ่าน → ไป Phase ถัดไป
3. ถ้ายังไม่ผ่าน → ระบุสิ่งที่ค้าง ปรับแผน Sprint ถัดไป
