# 1.2 User Story List

## วิธีการเขียน
User Story เขียนในรูปแบบมาตรฐาน Agile/Scrum:
**"As a [ประเภทผู้ใช้], I want [ฟีเจอร์/ความต้องการ], So that [เหตุผล/ประโยชน์]"**

**มาตรฐานอ้างอิง:**
- **Agile Alliance**: User Story Standards and Best Practices
- **Mike Cohn**: User Stories Applied (2004) - Agile Software Development Series
- **INVEST Criteria**: Bill Wake (2003) - Independent, Negotiable, Valuable, Estimable, Small, Testable
- **Scrum Guide**: Official Scrum framework (Ken Schwaber & Jeff Sutherland)
- **Planning Poker**: James Grenning (2002) & Mike Cohn - Story Points Estimation

### องค์ประกอบสำคัญ:
- **Story ID**: รหัสอ้างอิง
- **User Type**: บทบาทผู้ใช้ (Persona/Role)
- **Story**: เรื่องราวความต้องการ (As a... I want... So that...)
- **Priority**: ความสำคัญ (ตาม MoSCoW)
- **Story Points**: ประมาณการความซับซ้อน (Fibonacci: 1, 2, 3, 5, 8, 13, 21)
- **Sprint**: Sprint ที่จะทำ
- **Status**: สถานะปัจจุบัน
- **Assigned To**: ทีม/คนที่รับผิดชอบ
- **Related REQ**: Requirement ที่เกี่ยวข้อง

## User Story Writing Best Practices

### INVEST Criteria (Bill Wake, 2003)

User Story ที่ดีต้องเป็นไปตาม **INVEST**:
- **I - Independent** (อิสระ): ไม่ขึ้นกับ story อื่น สามารถทำก่อนหลังได้
- **N - Negotiable** (เจรจาได้): ไม่ใช่สัญญาตายตัว สามารถปรับเปลี่ยนรายละเอียดได้
- **V - Valuable** (มีคุณค่า): ให้คุณค่ากับผู้ใช้หรือธุรกิจ
- **E - Estimable** (ประมาณได้): สามารถประมาณ effort ได้
- **S - Small** (เล็กพอดี): ทำเสร็จใน 1 Sprint
- **T - Testable** (ทดสอบได้): มีเกณฑ์ชัดเจนว่า "เสร็จ" หรือ "ไม่เสร็จ"

### ✓ DO (Best Practices):
- **เขียนในมุมมองของผู้ใช้** - Focus on user perspective, not technical implementation
- **ระบุเหตุผลและประโยชน์** - Always include "so that" clause (ทำไมต้องมี feature นี้)
- **ทำให้ทดสอบได้ (Testable)** - มี Acceptance Criteria ที่ชัดเจน
- **เขียนให้สั้นและเข้าใจง่าย** - ใช้ภาษาธรรมดา ไม่ใช่ภาษาเทคนิค
- **แยก Story ให้พอดีกับ 1 Sprint** - ถ้าใหญ่เกินไป ให้แยกเป็น smaller stories
- **ใช้ Personas ที่ชัดเจน** - ระบุ user role ที่เฉพาะเจาะจง (Admin, Manager, Customer)
- **Collaborate กับทีม** - เขียนร่วมกับ Product Owner, Developers, และ Stakeholders

### ✗ DON'T (Common Mistakes):
- **เขียนเป็นภาษาทางเทคนิค** - หลีกเลี่ยงคำว่า "API", "database", "algorithm"
- **ใหญ่เกินไป (Epic)** - ถ้าใช้เวลามากกว่า 1 Sprint ให้แยกย่อย
- **ไม่มีเหตุผล (ไม่มี "so that")** - ต้องบอกว่าทำไมถึงต้องการ feature นี้
- **คลุมเครือ ไม่สามารถวัดผลได้** - ต้องมี Definition of Done ที่ชัดเจน
- **ขึ้นกับ story อื่นมากเกินไป** - ควรเป็นอิสระ (Independent)
- **เขียนเป็น Task แทน Story** - Story คือ "ทำไม" (why) ไม่ใช่ "ทำอย่างไร" (how)

## Story Points Reference (Fibonacci Sequence)

**ที่มา**: Fibonacci Sequence ใช้ใน Agile estimation เพราะสะท้อนความไม่แน่นอน (uncertainty) ที่เพิ่มขึ้นตามความซับซ้อน

**Planning Poker**: James Grenning (2002), Mike Cohn - วิธีประมาณ Story Points แบบกลุ่ม

| Points | Complexity | Effort Estimate | Example |
|---|---|---|---|
| 1 | ง่ายมาก (Trivial) | < 2 hours | แก้ไข text, เปลี่ยนสี button |
| 2 | ง่าย (Simple) | 2-4 hours | เพิ่ม validation field เดียว |
| 3 | ปานกลาง (Medium) | 4-8 hours | สร้าง simple form with validation |
| 5 | ค่อนข้างซับซ้อน (Moderate) | 1-2 days | CRUD operation for 1 entity |
| 8 | ซับซ้อน (Complex) | 2-3 days | Dashboard with multiple charts |
| 13 | ซับซ้อนมาก (Very Complex) | 1 week | Authentication system with 2FA |
| 21+ | Epic (ควรแยกย่อย) | > 1 week | ควรแยกเป็น smaller stories |

**หมายเหตุ**:
- Story Points วัด **ความซับซ้อน** (complexity) ไม่ใช่เวลา (time) โดยตรง
- ใช้ **Planning Poker** ให้ทีมร่วมกันประมาณ เพื่อความแม่นยำ
- **Velocity** = รวม Story Points ที่ทำเสร็จใน 1 Sprint (ใช้วางแผน Sprint ต่อไป)

## Template สำหรับเขียน User Story ใหม่

```markdown
Story ID: US-XXX
User Type: [ระบุบทบาท - เช่น Customer, Admin, Manager]
User Story: As a [user type], I want to [action/feature], so that [benefit/reason]
Priority: [Must Have/Should Have/Could Have/Won't Have]
Story Points: [1,2,3,5,8,13,21]
Sprint: [Sprint X]
Status: [To Do/In Progress/Done/Backlog]
Assigned To: [Team/Person]
Related REQ: [REQ-XXX]
```

### ตัวอย่าง User Story ที่ดี (ตาม INVEST):

**✓ GOOD EXAMPLE:**
```
Story ID: US-013
User Type: Customer
User Story: As a customer, I want to save items to my wishlist, so that I can purchase them later without searching again
Priority: Should Have
Story Points: 5
Sprint: Sprint 3
Status: To Do
Assigned To: Dev Team B
Related REQ: REQ-020
```

**Analysis (INVEST Check)**:
- ✓ Independent: สามารถทำได้โดยไม่ต้องรอ story อื่น
- ✓ Negotiable: สามารถเจรจาว่าจะทำ feature อะไรบ้าง (limit items, notification, etc.)
- ✓ Valuable: เพิ่มประสบการณ์ผู้ใช้ ลดการค้นหาซ้ำ
- ✓ Estimable: 5 points (ค่อนข้างซับซ้อน ~1-2 days)
- ✓ Small: ทำเสร็จใน 1 Sprint
- ✓ Testable: ทดสอบได้ว่าผู้ใช้สามารถบันทึกและดึงรายการได้

---

### ตัวอย่าง User Story ที่ไม่ดี:

**✗ BAD EXAMPLE 1 (ไม่มี "so that"):**
```
As a user, I want a login page
```
**ปัญหา**: ไม่มีเหตุผล (No benefit) - ไม่รู้ว่าทำไมต้องการ

**✓ แก้ไข:**
```
As a user, I want to login with email and password, so that I can securely access my account
```

---

**✗ BAD EXAMPLE 2 (Technical, not user-focused):**
```
As a developer, I want to implement JWT authentication with refresh token rotation using Redis cache
```
**ปัญหา**: เป็น Technical Task ไม่ใช่ User Story - ไม่มีมุมมองผู้ใช้

**✓ แก้ไข:**
```
As a user, I want to stay logged in for 30 days without re-entering my password, so that I can access my account quickly
```

---

**✗ BAD EXAMPLE 3 (Too big - Epic):**
```
As an admin, I want a complete reporting system with 20+ report types, export to multiple formats, scheduling, email delivery, and custom dashboards
```
**ปัญหา**: ใหญ่เกินไป (Not Small) - ทำไม่เสร็จใน 1 Sprint

**✓ แก้ไข (แยกเป็น smaller stories):**
```
US-014: As an admin, I want to view a sales report for the last 30 days, so that I can track revenue trends
US-015: As an admin, I want to export reports as PDF, so that I can share them with stakeholders
US-016: As an admin, I want to schedule reports to be sent via email weekly, so that I receive updates automatically
```
