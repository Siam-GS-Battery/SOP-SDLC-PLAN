## Branch Types

### Main Branches (Protected)

```mermaid
gitGraph
    commit id: "initial"
    branch develop
    checkout develop
    commit id: "feature work"
    checkout main
    merge develop id: "release v1.0"
    checkout develop
    commit id: "more work"
```

| Branch | วัตถุประสงค์ | Protected |
|--------|-------------|-----------|
| `main` | Production-ready code | ✅ Yes |
| `develop` | Development integration | ✅ Yes |

### Supporting Branches

| Branch Type | Pattern | ใช้สำหรับ | Merge To |
|-------------|---------|----------|----------|
| **Feature** | `feature/` | งาน feature ใหม่ | `develop` |
| **Fix** | `fix/` | แก้ bug ทั่วไป | `develop` |
| **Hotfix** | `hotfix/` | แก้ด่วน Production | `main` → `develop` |
| **Refactor** | `refactor/` | ปรับ code ไม่เปลี่ยน behavior | `develop` |
| **Chore** | `chore/` | งาน setup, update deps | `develop` |
| **Docs** | `docs/` | เอกสารล้วน ไม่แตะโค้ด | `develop` |
| **Release** | `release/*` | เตรียม release | `main` → `develop` |

## Branch Naming Convention

### รูปแบบ

```
<type>/<short-kebab-desc>
```

> **สำคัญ:** ตั้งชื่อ Branch ให้สั้น สื่อความหมาย บอกได้ว่าทำอะไร

### ตัวอย่าง

| Type | ตัวอย่าง |
|------|---------|
| Feature | `feature/add-login` |
| Fix | `fix/fix-login-error` |
| Hotfix | `hotfix/critical-security-patch` |
| Refactor | `refactor/extract-auth-helper` |
| Chore | `chore/upgrade-react` |
| Docs | `docs/update-readme` |
| Release | `release/v1.2.0` |

### กฎการตั้งชื่อ

- ✅ ส่วนหลัง `/` เป็นตัวพิมพ์เล็ก ตัวเลข ขีด `-` (และจุด `.` สำหรับเลขเวอร์ชันใน `release/` เช่น `release/v1.2.0`)
- ✅ ใช้ **lowercase** ทั้งหมด
- ✅ ใช้ **hyphen (-)** แทน space
- ✅ ชื่อสั้น กระชับ **2-5 คำ**
- ❌ ห้ามใช้ภาษาไทย
- ❌ ห้ามใช้ special characters

## Workflow

### Daily Flow

ขั้นตอนการทำงานรายวันของทีม:

```mermaid
flowchart LR
    A["1. git pull origin develop\n(ทุกเช้า)"] --> B["2. checkout -b\nfeature/xxx"]
    B --> C["3. Work & Commit\n(ทุก 1-2 ชม.)"]
    C --> D["4. Push & Open PR\n(+ Template)"]
```

| ขั้นตอน | คำสั่ง/การกระทำ | หมายเหตุ |
|---------|----------------|----------|
| 1 | `git pull origin develop` | ทำทุกเช้าเพื่อให้ code เป็นปัจจุบัน |
| 2 | `checkout -b feature/xxx` | สร้าง branch ตามรูปแบบที่กำหนด |
| 3 | Work & Commit | commit ทุก 1-2 ชม. ตาม Conventional Commits |
| 4 | Push & Open PR | ใช้ PR Template ทุกครั้ง |

### Feature Development Flow

```mermaid
flowchart LR
    A[develop] -->|1. create branch| B[feature/xxx]
    B -->|2. develop & commit| B
    B -->|3. push & create PR| C[Pull Request]
    C -->|4. code review| C
    C -->|5. approve & merge| A
```

### ขั้นตอน

#### 1. สร้าง Feature Branch

```bash
# อัปเดต develop ล่าสุด
git checkout develop
git pull origin develop

# สร้าง feature branch
git checkout -b feature/KZN-123-user-login
```

#### 2. พัฒนาและ Commit

```bash
# ทำงานและ commit
git add .
git commit -m "feat(auth): add login form component"

# commit เพิ่มเติม
git commit -m "feat(auth): add form validation"
```

#### 3. Push และสร้าง PR

```bash
# push branch ขึ้น remote
git push -u origin feature/KZN-123-user-login

# สร้าง Pull Request บน GitHub
```

#### 4. Code Review & Merge

- รอ reviewer approve
- แก้ไขตาม feedback
- Merge เมื่อได้ approval

### Hotfix Flow

```mermaid
flowchart TD
    A[main] -->|1. create hotfix| B[hotfix/xxx]
    B -->|2. fix & test| B
    B -->|3. merge to main| A
    B -->|4. merge to develop| C[develop]
```

```bash
# สร้าง hotfix จาก main
git checkout main
git pull origin main
git checkout -b hotfix/KZN-999-fix-critical-bug

# แก้ไขและ commit
git commit -m "fix(auth): patch security vulnerability"

# Merge กลับ main และ develop
# (ผ่าน Pull Request)
```

## Branch Protection Rules

### main branch

| Rule | ค่า |
|------|-----|
| Require PR before merge | ✅ Yes |
| Require approvals | 0 (ใช้ required check `Senior Approval` แทน) |
| Require status checks | ✅ CI must pass + `Senior Approval` |
| Include administrators | ✅ Yes |
| Allow force push | ❌ No |
| Allow deletions | ❌ No |

### develop branch

| Rule | ค่า |
|------|-----|
| Require PR before merge | ✅ Yes |
| Require approvals | 0 (ใช้ required check `Senior Approval` แทน) |
| Require status checks | ✅ CI must pass + `Senior Approval` |

> **ข้อยกเว้นชั่วคราว (ทีมมี Senior คนเดียว):** `Senior Approval` ผ่านเมื่อผู้เปิด PR เป็น Senior (self-merge ได้ ถ้า CI เขียว + กรอก PR Template + ติ๊ก Self-review checklist) หรือเมื่อมี Approve จาก Senior ที่ไม่ใช่ผู้เปิด PR — PR ของ non-Senior ยังต้องมี Senior Approve ให้ทบทวนกฎนี้เมื่อมี Senior/reviewer คนที่ 2 (รายละเอียด: [7.3](7.3_Pull_Request_Process.md), [7.5](7.5_GitHub_Actions_CI_Template.md))

## Best Practices

### ✅ ควรทำ

1. **Pull ก่อนสร้าง branch ใหม่**
   ```bash
   git checkout develop
   git pull origin develop
   git checkout -b feature/xxx
   ```

2. **Commit บ่อยๆ** - เป็น checkpoint เล็กๆ

3. **Rebase เพื่ออัปเดต branch**
   ```bash
   git checkout feature/xxx
   git fetch origin
   git rebase origin/develop
   ```

4. **ลบ branch หลัง merge**
   ```bash
   git branch -d feature/xxx
   git push origin --delete feature/xxx
   ```

5. **ใช้ meaningful branch names**

### ❌ ไม่ควรทำ

1. **อย่า commit ลง main/develop โดยตรง**
2. **อย่า force push ไปที่ protected branches**
3. **อย่าสร้าง branch ยาวเกินไป** - merge บ่อยๆ
4. **อย่าลืม pull ก่อนเริ่มงาน**

## Quick Reference

### คำสั่งที่ใช้บ่อย

```bash
# ดู branches ทั้งหมด
git branch -a

# สร้าง branch ใหม่
git checkout -b <branch-name>

# สลับ branch
git checkout <branch-name>

# ลบ branch (local)
git branch -d <branch-name>

# ลบ branch (remote)
git push origin --delete <branch-name>

# อัปเดต branch list
git fetch --prune
```
